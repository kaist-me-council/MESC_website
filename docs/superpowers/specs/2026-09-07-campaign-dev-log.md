- **결정** (사용자): 마감 9/13, 메일 9/8(수령 안내만), 환불 계좌는 화면에서 안 받음, 2차 발주 조건 명시 안 함(수령 종강 직전), 남는 재고는 1차 마감 후 실사, **학번은 민감정보**.

- **검증**: 로컬 프로덕션 빌드에서 로그인→적재→조회→응답→CSV→레이트리밋 전 과정 curl 스크립트.

## 3. 2단계 = 범용 "학생회 이벤트(신청·구매 캠페인)"

- **결정**: B안(캠페인 = 제목·기간·계좌·옵션·재고·구분별 가산). 폼 빌더(C안)는 안 함. PG·회원가입·메일 자동 발송 제외.
- **구현 (v1)**: `Campaign/CampaignOption/CampaignOrder`, 공개 `/apply`, `/apply/[slug]`(주문 → 주문번호·금액·계좌), 관리자 `/admin/campaigns`(설정·옵션 일괄·반팔티 14옵션, 신청 목록·상태·발주표·CSV·이메일 복사). 3개 서브에이전트(백엔드/공개/관리자) 병렬, 계약은 설계 문서에 먼저 고정.
- **검증**: e2e `scripts/campaign-api.test.sh` ALL PASSED (생성→주문→재고 409→조회→상태→CSV→삭제).

## 4. v2: 수령 확인 흡수 · 굿즈 상품형 · 취소/일괄
- **요청**: 1차 확인을 캠페인의 "조사 확인" 기능으로 1:1 대응. 옷은 사이즈가 보이는 진짜 쇼핑몰처럼. 입금 취소, 다중 선택 일괄 처리, 본인 주문 취소. 디자인 신경.
- **결정**: `PriorPurchase`·`/admin/shop`·`/api/shop/*` 제거, `/shop/check` 는 `/apply/2026-spring-tshirt/confirm` 리다이렉트(메일 링크 유지). 캠페인 하나 = 상품 하나(장바구니형 다상품 안 함). 본인 취소는 pending 만.
- **구현**: 프리셋 "상반기 반팔티(수령 확인용)", 주문 적재(배부 시트/일반 CSV, dryRun), `/apply/[slug]/confirm`, 굿즈 상품형(이미지·색상 칩·사이즈 칩·수량·하단 고정 바), 체크박스 일괄 상태·입금 취소·선택 이메일 복사, 못 받음 집계, 이미지 업로드.
- **사고**: 세션 한도로 에이전트 3개가 중간에 멈춤 → 재개(SendMessage)로 이어서 완료.
- **조언 문서** `2026-09-07-google-form-advisor.md` 검토: 방향 동일. 반영 결정은 v2 문서 8절(사이즈 별칭은 import 만, 과비 기준 6,000원 정책 미채택, 폼 1:1 포팅 금지, 메일 전 프로덕션 프리셋+적재 필수).
- **검증**: e2e 확장 ALL PASSED, 프리뷰에서 리다이렉트·확인 페이지·구 API 404 확인.

## 5. v2.1: 이미지 여러 장 · 구분별 가산 버그 · 잘림
- **요청**: 사진 1장은 부족(시안+사이즈표). 구분별 가격이 적용 안 됨. 이미지가 강제로 바뀜.

- **구현**: `Campaign.images`(JSON 최대 8장, imageUrl=대표), 관리자 다중 업로드·순서·삭제, 공개 갤러리 `object-contain` + 원본 새 탭, 서버가 priceAdjust 문자열도 수용.
- **검증**: e2e ALL PASSED + priceAdjust 문자열·images 왕복 curl 확인, 프리뷰 반영.

## 7. v4: 검토 반영 — 데이터 보호·동시성·본인 변경 보호 (9/8)
- **요청**: Codex 검토 문서가 실제 지적으로 채워짐(배포 차단 3건 포함). "이거 보고 추가 작업해줘". 이후 "환불처리 체크"도 추가 요청.
- **선행 확인(실측)**: 프로덕션에 캠페인 1개·주문 146건(수령 135·입금 11)·확인 응답 0건이 이미 존재. `PriorPurchase` 는 프로덕션에 테이블 자체가 없음(000000 생성→000003 삭제가 같은 배포) → 검토 문서의 데이터 이전 우려 해소. 배포 전 서버측 백업 `mesc-backup-20260908` 생성(146건 검증).
- **P1 수정**: ① 교체 적재가 검증 전에 삭제하던 것 → 파싱·검증 선행, 문제 행·0건 400 거부, 삭제+생성 단일 트랜잭션 ② 재고 확인·생성 비원자성 → 재고 제한 옵션 포함 시 인터랙티브 트랜잭션에서 재계산(동시 3요청 → 1건만 201) ③ 오래된 pending 취소가 관리자 입금 확인을 덮어씀 → `status=pending` 조건부 갱신, 경합 409.
- **P2·승인 범위**: 관리 코드(평문 1회·해시 저장, 취소 필수, 주문번호 단독 상태 변경 차단), idempotencyKey 유니크, maxPerPerson 동일인 누적, CSV 수식 중화, 공개 화면 실패 유형 구분, 관리자 공통 레이아웃·4그룹 내비·캠페인 상세 4탭, 필터 변경 시 선택 초기화.
- **정책 판단**: 수령 확인은 이름+학번/이메일 인증을 유지. 적재 주문 146건에는 관리 코드가 없고 검토 문서도 일괄 생성을 금지하므로, 코드를 요구하면 기존 확인 흐름이 끊긴다. 응답은 되돌릴 수 있고 관리자가 전수 확인 가능해 위험이 낮다고 판단.
- **추가**: 환불 완료(`refundedAt`) 토글·뱃지·환불 대기 정산 카드(건수·금액)·CSV 열. 환불 필요 판정 = 입금 후 취소 또는 못 받음 응답에서 환불 희망.
- **운영 변경**: 사용자가 수령 확인을 메일 대신 전화·문자로 처리 → 확인 마감·메일 문구는 무의미해짐. 전화 응답은 수령 확인 탭의 대리 입력으로 기록.
- **검증**: tsc·eslint·프로덕션 빌드 통과, e2e ALL PASSED(병렬 재고 경합, 취소 경합, 잘못된 CSV 거부 후 건수 불변, 관리 코드, 재전송, 환불 토글), 단위 테스트 2종. 프로덕션 DB 미사용. PR #3.

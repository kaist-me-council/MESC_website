# 조언: 구글폼 반팔티 조사를 학생회 캠페인으로 옮길 때

작성일 2026-09-07 · 독자: 이 저장소에서 구현하는 Claude · 화자: 조언자(코드 말고 판단)

이 문서는 **구현 스펙이 아니다.** 기존 구글폼이 왜 사고를 냈는지, 사이트 캠페인(`/apply`)으로 가면 무엇을 살리고 무엇을 버려야 하는지 적어 둔다. 홈페이지를 뜯거나 폼을 24문항 그대로 재현하지 마라. 내일(9/8) 1차 수령 확인 메일과 이 작업을 한 브랜치에서 섞지 마라.

근거 자료:

- 기존 폼 PDF: `2026년 상반기 기계과 반팔티 구매에 대한 조사 - Google Forms.pdf`
- 1차 확인·재고 사고: `docs/superpowers/specs/2026-09-07-tshirt-shop-design.md`
- 캠페인 일반화: `docs/superpowers/specs/2026-09-07-campaign-system-design.md`
- 수령 확인을 캠페인에 흡수: `docs/superpowers/specs/2026-09-07-campaign-v2-design.md`

## 1. 결론 (이거만 읽고 구현해도 됨)

구글폼은 **설문**이다. 학생회 사업은 **주문**이다. 둘이 다르다.

다음에 반팔티·MT·굿즈를 받을 때는 설문을 복제하지 말고, 이미 있는 캠페인 한 건으로 받아라.

- 한 화면에서 색 → 사이즈 → 수량을 고른다. 색마다 사이즈 라디오를 세 번 그리지 않는다.
- 금액은 서버가 계산해서 보여 준다. 본문이 설명하는 식을 학생이 계산하게 두지 않는다.
- 제출 후 주문번호가 나온다. “입금했어요” 체크박스만으로 끝내지 않는다.
- 다른 사이즈를 사고 싶으면 메일이 아니라 같은 주문서에 줄을 더한다.
- 교수는 학번 `0`을 넣게 하지 않는다. 이메일+이름.
- 학번 원문은 DB에 남기지 않는다. 지금 `studentIdHash` 규칙을 따른다.

하지 마라: PG, 회원가입, 만능 폼 빌더, 여러 상품 장바구니, 구글폼 문항 1:1 포팅, 홈 개편.

## 2. 그 폼이 실제로 물은 것

기간 2026.06.22–06.30. 문의 `ys.an@kaist.ac.kr`. 입금 이슈 전화 010-6351-6533. 흰/검 앞뒤 도안 + TOMS-300ACT 실측표(SS~5L).

분기 구조:

1. 구매 의사 (산다 / 안 산다)
2. 산다 → 구분(학부 / 대학원 / 교수)에 따라 **같은 상품 질문이 세 번 복제**됨

공통 신원: 학번(교수는 0), 이름, 전화, 이메일.

상품(구분마다 반복):

- 흰 사이즈 하나 (SS / S / M / L / XL(LL) / 2XL(3L) / 3XL(4L) / 4XL(5L) / 구매 안 함)
- 흰 수량
- 검 사이즈 하나 · 검 수량
- 계좌 안내 + “입금했습니다” 체크 + 입금자명

가격 안내(본문, 계산 아님):

- 학부 과비 납부자: 1벌 약 6,000원, 2벌부터 +8,000원. 예: 3벌 22,000원. 흰 1 + 검 1 = 2벌 14,000원
- 학부 과비 미납: 제작원가(본문에 “full production cost”)
- 대학원: 벌당 9,000원
- 교수: 벌당 10,000원

다른 사이즈를 여러 개 사려면 **폼을 다시 쓰지 말고 메일** 하라고 적혀 있다.

## 3. 이 폼이 운영을 깨는 지점

이후 배부 시트와 재고가 안 맞은 이유와 거의 같다. 추측이 아니라 폼 설계에서 나온다.

**한 색에 사이즈 하나.** 흰 XL 1 + 흰 2XL 1을 폼으로 못 산다. 메일이 27건 생긴 경로다. 메일은 파서가 없고, `2XL 1개 --> XL 1개로 수정` 같은 자유 텍스트가 된다.

**수량과 사이즈가 다른 문항.** “흰 사이즈 L” + “흰 수량 2”는 같은 사이즈 두 벌만 된다. 주문 한 줄(색·사이즈·수량)이 없다.

**금액을 사람이 계산한다.** 학부 첫 벌 6,000 / 이후 8,000, 흰+검은 “세트 수”로 세는 식. 입금 금액이 주문과 어긋나도 폼은 “입금했습니다”만 받는다.

**입금 확인이 자기신고다.** 주문번호가 없다. 관리자는 입금자명·금액·시트를 눈으로 맞춘다.

**교수 학번 0.** 교수 여러 명이면 조회 키가 충돌한다.

**사이즈 별칭.** XL(LL), 2XL(3L), SS. 나중에 파서가 필요해진 이유. 화면에는 S~4XL 하나만 보여라. 별칭은 import 할 때만 정규화.

**가격 정책이 폼과 이후 정산이 다르다.** 폼은 학부 과비 납부 시 ~6,000원. 이후 문서의 판매가는 학부 8,000 / 대학원 9,000 / 교수 10,000, 원가 7,800(2XL+는 9,300). 2차는 과비 여부로 6,000을 다시 쓰지 마라. 단가는 캠페인 옵션 `price` + 구분 `priceAdjust` 한곳.

**제출 후 내 주문을 못 본다.** 그래서 지금 1차 확인(`/shop/check`)을 따로 만들어야 했다.

**문항이 구분×상품으로 폭증.** 신원 한 번, 상품 한 번이면 될 것이 24문항처럼 보인다. 캠페인 UI가 이 분기를 따라가면 실패다.

## 4. 캠페인 필드에 어떻게 얹나

이미 있는 모델로 충분하다. 새 설문 엔진을 만들지 마라.

| 구글폼 | 캠페인 |
|---|---|
| 산다/안 산다 | 페이지에 들어온 사람이 사는 사람. “안 산다” 문항 없음 |
| 학부/대학원/교수 | `affiliation` (졸업생·기타는 캠페인 기본값 유지) |
| 학번 · 이름 · 전화 · 이메일 | 주문 필드. 학번은 해시만. 교수는 `requireStudentId=false` 또는 이메일+이름 |
| 흰/검 사이즈 | `CampaignOption.group` = 흰색\|검정, `name` = S~4XL. SS는 S로 정규화하거나 옵션에서 빼는 결정을 문서에 한 줄로 |
| 수량 | 옵션별 `qty`. `allowQty=true` |
| 가격 설명문 | 서버 `unitPrice`. 화면에 합계만 |
| 계좌 · 입금자명 | `bankInfo`는 제출 **후** 완료 화면에만. 입금자명은 “입금자명은 이름과 같게”를 `afterNote`로 |
| 입금했습니다 체크 | 없음. 상태 `pending` → 관리자가 `paid` |
| 도안·실측표 | `imageUrl` + 설명 본문. 섹션마다 반복 금지 |
| 다른 사이즈는 메일 | 금지. 담기에 줄 추가 |
| 기간 | `opensAt` / `closesAt` |
| 추가 구매 메일 | 같은 캠페인에서 주문 추가 또는 기존 주문 수정. 정책 한 줄만 |

수령 확인(지금 1차로 하는 일)은 구글폼에 원래 없었다. 배부가 끝난 뒤 `confirmEnabled`로 받는다. 폼을 확장해서 “받았나요?”를 넣지 말고, 캠페인 확인 기능을 쓴다.

## 5. 화면이 폼보다 나아야 하는 이유 (제품)

학생이 하는 일 순서:

1. 옷 그림과 실측을 본다
2. 흰/검과 사이즈를 고른다 (품절이면 그 칸만 막힌다)
3. 이름·구분·학번/이메일을 적는다
4. **이 금액**을 보고 입금한다
5. 주문번호를 저장한다
6. 나중에 같은 페이지에서 내 주문을 연다

구글폼은 1을 반복 삽입하고, 2를 라디오로 쪼개고, 4를 숙제로 남기고, 5·6이 없다.

관리자가 하는 일:

- 입금 내역과 주문을 주문번호·이름으로 맞춘다
- 못 받은 사람 / 사이즈 부족을 한 화면에서 본다
- 메일 명단을 복사한다

시트를 파싱하는 일은 import 한 번에 끝낸다. 평소 운영의 기본값이 되면 안 된다.

## 6. 학생회 전체 사업에 대한 방향

반팔티 페이지만 만들면 2주 뒤 죽는다. 학생회 사업 루프는 같다.

공지 → 신청(옵션·수량) → 계좌이체 → 입금 확인 → 배부/수령 확인 → 환불·교환.

캠페인(`/apply`)이 그 루프다. MT, 체육대회, 간식, 다음 단체복도 캠페인 한 개다. 구글폼을 행사마다 복제하지 않는 것이 이 일의 의미다.

사이트에는 이미 학과 포털(공지·구성원·과비·지도)이 있다. 캠페인은 그 옆의 **사업 운영 층**이다. 둘을 한 화면에 섞지 마라.

과비 납부 여부로 티셔츠 단가를 가르는 것(이번 폼의 6,000원)은 캠페인에 기본으로 넣지 마라. 과비 API와 주문 API를 실시간으로 묶으면  identifiability·실패 모드가 커진다. 단가는 캠페인에 적고, 과비 감면이 정히 필요하면 그때 수동 메모나 별도 쿠폰성 가산으로.

## 7. Claude에게 맡길 범위 (조언)

이 문서를 받았다면:

1. **내일 메일(9/8) 경로를 건드리지 마라.** 워킹트리에서 `/api/shop/check`를 지운 채 배포하면 링크가 죽는다. 수령 확인은 커밋된 `/shop/check`로 보내거나, 캠페인 확인 페이지가 **완전히** 열린 뒤에만 리다이렉트하라.
2. 2차 구매·이후 행사는 `kind=goods` 캠페인 한 개다. 구글폼 문항을 컴포넌트로 옮기지 마라.
3. 사이즈 칩 + 수량 + 서버 합계 + 제출 후 계좌·주문번호. 그다음이 관리자 입금 체크다.
4. 기존 파서(`lib/tshirt-parse.ts`)는 import 전용으로 남겨라. 공개 화면의 입력기가 되어서는 안 된다.
5. 디자인은 `DESIGN_SYSTEM.md`의 네이비 안에서, 있는 카드·버튼만 써라. 홈을 새로 그리지 마라.
6. 작게: 반팔티 2차 한 캠페인이 처음부터 입금 확인까지 한 바퀴 돌면 성공이다. 그 전에 폼 빌더를 만들지 마라.

질문이 생기면 폼을 더 닮게 만들지 말고, “이 주문을 관리자가 시트 없이 처리할 수 있나?”로 판단하라.

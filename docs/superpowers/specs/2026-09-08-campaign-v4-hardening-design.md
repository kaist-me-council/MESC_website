## 1. 배포 차단 항목 수정 (P1)

### 1-1. 교체 적재가 실패해도 기존 주문을 먼저 지움
현재 `orders/import/route.ts` 는 `replace` 면 파싱 결과와 무관하게 먼저 `deleteMany` 한다.
- 파싱·검증을 **전부 끝낸 뒤** 실행한다. `problems.length > 0` 이거나 `rows.length === 0` 이면 **400 으로 거부**(부분 허용 옵션 없음).
- 삭제와 생성을 `prisma.$transaction([...])` 한 번에 묶는다. 실패 시 기존 주문·확인 응답·메모가 그대로 남아야 한다.
- `ensureOptions` 는 dry-run 에서 옵션을 만들지 않는다(현재 `true` 플래그로 만들고 있으면 미리보기 전용 계산으로 바꾼다).
- 수용 기준: 잘못된 CSV 로 replace 시도 → 400, 기존 건수 불변. e2e 로 고정.

### 1-2. 재고 확인과 주문 생성 사이 원자성 없음
- 재고 제한이 있는 옵션이 하나라도 포함되면 `prisma.$transaction(async (tx) => { ... })` 안에서 잔여 재고를 다시 계산하고 부족하면 throw → 409.
- 재고 제한이 전혀 없으면 기존 경로(트랜잭션 없이 create) 유지.
- 수용 기준: 재고 1 옵션에 동시 2요청 → 1건만 201, 나머지 409. e2e 에 병렬 요청 테스트 추가.

### 1-3. 오래된 pending 조회가 관리자 입금 확인을 덮어씀
- 취소는 `updateMany({ where: { id, campaignId, status: "pending" }, data: { status: "cancelled" } })` 로 바꾸고 `count === 0` 이면 409 + 현재 상태 안내.

## 2. P2

### 2-1. `maxPerPerson` 누적
- 같은 신청자(학번 해시 우선, 없으면 이메일 + 이름 정규화)의 **취소 제외 기존 주문 수량 합** + 신규 수량이 `maxPerPerson` 을 넘으면 거부.
- 중복 신청 자체는 계속 허용(사용자 정책). `maxPerPerson` 이 null 이면 무제한.
- 1-2 의 트랜잭션 안에서 함께 검증.

### 2-2. CSV 수식 주입 중화
- 텍스트 열 값이 `= + - @ TAB CR` 로 시작하면 앞에 `'` 를 붙여 중화. 숫자 열(합계)은 그대로.

## 3. 본인 변경 보호 — 관리 코드 (회원가입 없이)

- `CampaignOrder.manageCodeHash String?` 추가. 신청 성공 시 서버가 8자 코드(대문자+숫자, 혼동 문자 제외) 생성 → **응답에 평문 1회만** 반환, DB 에는 `sha256(ANON_SALT:mc:코드)` 만.
- **취소**(`orders/cancel`)는 `orderNo + manageCode` 를 요구한다. 이름·학번만으로는 취소 불가.
- **수령 확인**(`confirm`)은 기존대로 `이름 + 학번|이메일` 을 유지한다. **이유**: 프로덕션의 146건은 전부 적재 주문이라 관리 코드가 없고, 9/30 수령 확인이 이 흐름 위에서 돌아간다. 검토 문서의 "상태 변경은 코드 요구" 원칙에서 확인 응답만 예외로 두되, 응답은 되돌릴 수 있고 관리자가 전체를 볼 수 있어 위험이 낮다. 적재 주문에 코드를 일괄 생성하지 않는다(검토 문서 지침 준수).
- 조회(`lookup`)는 읽기 전용이므로 기존 3방식(이름+학번 / 이름+이메일 / 주문번호) 유지.
- **주문번호 단독으로는 어떤 상태 변경도 불가**하게 한다.
- 코드 분실 복구는 자동화하지 않는다. 화면에 "학생회에 문의" 안내, 관리자가 처리.

## 4. 재전송 보호 (idempotency)

- `POST orders` 는 `idempotencyKey`(클라이언트 생성 UUID, 8~64자)를 받는다. `CampaignOrder.idempotencyKey String?` + `@@unique([campaignId, idempotencyKey])`.
- 같은 캠페인·키로 재요청이 오면 새로 만들지 않고 기존 주문을 그대로 반환(201 대신 200). 코드 평문은 재발급하지 않고 "이미 접수됨" 으로 안내.

## 5. 공개 화면 실패 처리

- 신청·조회·취소·확인의 fetch 실패(네트워크), 4xx, 5xx, 429 를 각각 구분해 표시한다. "신청 내역 없음"과 통신 실패를 섞지 않는다.
- 실패 시 입력·선택값 보존, 버튼 잠금 해제.
- 신청 완료 카드에 **관리 코드**를 주문번호와 함께 크게 보여 주고 복사 버튼 제공. "취소하려면 이 코드가 필요합니다" 안내.
- 내 신청 확인의 취소 버튼은 코드 입력칸을 펼쳐 받는다. 409 면 "이미 입금 확인됨 — 학생회에 문의" 표시.
- 네트워크가 끊겨 결과를 못 받은 경우 "이미 접수됐을 수 있으니 조회 후 다시 시도" 안내.

## 6. 관리자 화면

- 필터·검색을 바꾸면 선택 주문을 초기화한다.
- 설정 저장·이미지 업로드 중 최신 입력을 덮어쓰지 않도록 함수형 갱신(`setC(prev => ...)`) 사용.
- 캠페인 상세 탭 4개: **신청 목록(기본)** / **수령 확인**(confirmEnabled 일 때만) / **설정** / **데이터 가져오기**. 탭은 `?tab=` 로 보존.
- 수령 확인 탭: 미응답·받음·못 받음 필터, 항목별 희망 처리와 수량 집계, 처리 완료 토글.
- 데이터 가져오기 탭: 미리보기·실행, 교체 시 삭제 범위·건수 명시(이미 구현됨) + 문제 행이 있으면 실행 버튼 비활성.
- 공통 관리자 레이아웃: `app/admin/(protected)/layout.tsx` 에 헤더 + 4그룹 내비(데스크톱 사이드/모바일 접이식), 현재 위치 표시. 메뉴 정의는 `lib/admin-menu.ts` 한곳. URL·서버 인증 불변.

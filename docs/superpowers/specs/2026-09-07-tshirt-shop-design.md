- **2단계**: 2차 구매는 범용 **학생회 이벤트(신청·구매 캠페인)** 시스템의 첫 캠페인으로 진행 → `2026-09-07-campaign-system-design.md`. 1차 확인 마감(9/13) 후 남는 재고를 확정한 뒤 연다.

## 1. 배경: 지금 무슨 일이 있었나

2026년 상반기 반팔티(흰·검 2색, S~4XL 7사이즈)를 구글폼으로 주문받아 배부하던 중 재고가 명단과 맞지 않는 것을 발견했다. 다시 센 결과는 아래와 같다.

| | S | M | L | XL | 2XL | 3XL | 4XL | 합 |
|---|---|---|---|---|---|---|---|---|
| 흰 재고 | 1 | 1 | 5 | 3 | 0 | 1 | 0 | 11 |
| 흰 미수령자 필요량 | 1 | 2 | 4 | 3 | 1 | 1 | 0 | 12 |
| **흰 과부족** | 0 | **-1** | +1 | 0 | **-1** | 0 | 0 | |
| 검 재고 | 1 | 4 | 10 | 0 | 3 | 2 | 1 | 21 |
| 검 미수령자 필요량 | 1 | 2 | 9 | 6 | 2 | 0 | 1 | 21 |
| **검 과부족** | 0 | +2 | +1 | **-6** | +1 | +2 | 0 | |

(사이즈 표기: 폼의 XL(LL)=XL, 2XL(3L)=2XL, 3XL(4L)=3XL, 4XL(5L)=4XL로 통일)

- 응답 140명 + 추가 연락 27건(중복 포함) → 배부 명단 146명, **픽업 완료 127명 / 미수령 19명**.
- 흰 2XL 부족은 추가 주문 때 XL로 바뀌어 발주된 것이 확인됨 → 해당자는 XL 수령 또는 환불로 이미 결정.
- 나머지 불일치(특히 검 XL -6)는 원인 추적이 어려움 → 구매자 본인이 확인해 주는 절차가 필요.
- 1차 때 "주문 못한 것"(재고 없어 못 준 수요)이 흰 7벌·검 14벌 = 21벌 있음 → 2차 구매 수요의 근거.
- 단가: 원가 7,800원(2XL 이상 9,300원), 판매가 학부 8,000 / 대학원 9,000 / 교수 10,000원(장당), 배송료 5,000원.

## 2. 목적

1. **1차 정리 (1단계)**: 구매자가 스스로 "내가 산 것"을 보고 받았는지/못 받았는지 답하게 해서, 못 받은 사람에게 재고가 있으면 주고 없으면 환불한다. **9/13 회신 마감** 이후 미확인 건은 종결한다.
2. **2차 구매 (2단계)**: 사고 싶었는데 못 산 사람을 위해 온라인 쇼핑몰처럼 색·사이즈·수량을 골라 주문하고, 금액과 입금 계좌를 안내받는 비회원 주문 창구를 학과 홈페이지 안에 연다. 수령은 **종강 직전**.
3. **운영 부담 최소화**: 관리자가 엑셀 없이 admin 화면에서 응답·주문·입금·수령을 체크하고, 재고와 부족분을 한눈에 본다.

## 3. 범위

**1단계 포함**
- 공개 `/shop/check`: 본인 확인 → 1차 주문 내역 → 받음/못 받음 응답.
- 관리자 `/admin/shop`의 "1차 확인" 탭: xlsx import, 응답 현황, 못 받음 건 처리 목록, 부족 사이즈 집계, CSV.
- 개인정보처리방침 수정.

**2단계 포함**
- 공개 `/shop`(주문)·`/shop/orders/[번호]`(내 주문, 계좌 안내).
- 관리자 탭 추가: 설정(기간·단가·계좌), 재고, 2차 주문(입금·수령 체크, 발주표 CSV).

**제외(안 함)**
- 온라인 결제(PG). 입금은 계좌이체, 확인은 관리자가 수동.
- 회원가입·로그인. 본인 확인은 학번+이름(교수는 이메일+이름).
- 사이트에서 메일 자동 발송. 메일은 Gmail로 직접 보내고 링크만 넣는다.
- 2차 발주 조건(최소 수량·배송료 분담) 명시. 안내 문구는 "수령: 종강 직전 예정"만.
- 반팔티 외 상품 일반화.

## 4. 사용자 흐름

### 4-1. 구매자: 1차 구매 확인 (`/shop/check`) — 1단계
1. 학번 + 이름 입력 (교수·학번 없음: 이메일 + 이름).
2. 1차 주문 내역 표시: 흰/검 사이즈·수량, 배부 기록상 픽업 여부.
3. 답변 선택: **받았어요** / **못 받았어요**.
   못 받았어요 → 사이즈별로 "학생회실에서 수령" / "환불 희망" / "다른 사이즈로 교환 희망(사이즈 선택)" 중 택1, 연락 메모(선택). 환불 계좌는 화면에서 받지 않고 개별 연락으로.
4. 제출 → 접수 확인 화면. 같은 사람이 다시 열면 이전 답변을 보여주고 마감 전까지 수정 가능. 마감(9/13 23:59) 후엔 조회만.

### 4-2. 구매자: 2차 주문 (`/shop`) — 2단계
1. 상품 화면: 흰/검 × 사이즈 그리드, 수량 선택. 각 칸에 "즉시 수령 가능(재고 n)" 또는 "2차 발주 · 종강 직전 수령" 표시. 판매 기간 밖이면 닫힘 안내.
2. 주문자 정보: 구분(학부/대학원/교수/졸업생), 이름, 학번, 전화, 이메일. 구분에 따라 단가 자동 적용.
3. 금액 확인 → 주문 생성 → **완료 화면: 주문번호, 총액, 입금 계좌(사무국장), 입금자명 안내**. 주문번호+학번으로 다시 열 수 있음.
4. 관리자가 입금 확인 → "입금 확인" → 수령 시 "수령 완료".

### 4-3. 관리자 (`/admin/shop`)
- **1차 확인** (1단계): xlsx import(미리보기 → 확정), 응답 현황(받음/못 받음/미응답), 못 받음 건과 처리 방식, 부족 사이즈 집계, CSV.
- **설정·재고·2차 주문** (2단계): 판매 기간, 구분별 단가, 2XL+ 추가금, 계좌·예금주, 안내 문구(한/영); 색×사이즈 재고; 주문 목록·상태 토글·발주표 CSV.

## 5. 시스템 설계 개요

기존 패턴을 그대로 따른다: Next.js App Router + Prisma(Turso), admin은 `app/admin/(protected)/` 아래, API는 `app/api/` 아래, 공개 조회 API는 과비 확인(`/api/check-fee`)처럼 IP 레이트리밋.

**데이터**
- 1단계: `PriorPurchase` — 구분, 이름, **학번 해시**(원문 미저장), 이메일, 전화, 흰/검 사이즈·수량(JSON), 배부 기록 픽업 여부, 확인 응답(received / not_received / 미응답), 사이즈별 처리 선택·메모, 응답 시각.
- 2단계: `ShopSettings`(단일 행), `ShopStock`(color × size), `ShopOrder` + `ShopOrderItem`(주문번호, 구분·이름·**학번 해시**·전화·이메일, 상태 pending → paid → delivered / cancelled, 항목·단가).

**API**
- 1단계 공개: `POST /api/shop/check`(조회), `PUT /api/shop/check`(응답 저장). 관리자: `/api/admin/shop/prior`(import·목록·CSV).
- 2단계 공개: `GET /api/shop`, `POST /api/shop/orders`, `GET /api/shop/orders/[no]`. 관리자: 설정·재고·주문 상태.

**학번은 민감정보 — 취급 원칙**
- DB에는 학번 원문을 저장하지 않는다. `sha256(ANON_SALT + 학번)`만 저장하고, 조회 시 입력값을 같은 방식으로 해시해 대조한다(기존 `lib/anon.ts`의 `ipHash`와 같은 패턴). 관리자 화면에도 학번은 나오지 않는다. 사람 식별은 이름·이메일로 충분하다.
- 원본 엑셀은 사용자 PC에만 둔다. import는 브라우저에서 업로드 → 서버가 파싱·해시 → 원문 폐기. 서버 로그·스크래치 파일·대화에 학번을 남기지 않는다.
- 조회 API는 학번+이름이 둘 다 맞아야 응답, IP당 분당 5회 제한. 실패 시 "정보 없음"만 반환(존재 여부 노출 안 함).
- 전화·이메일은 admin에서만 노출. 계좌번호는 주문 완료·내 주문 화면에서만.
- 개인정보처리방침에 "단체복 구매 관리: 이름·학번(해시)·연락처·이메일·주문 내역, 보유 6개월(정산 완료 후)" 추가. 만료 시 주간 백업 크론의 정리 루틴에서 삭제.

## 총평과 유지할 방향

구글폼 문항을 복제하지 않고 캠페인 하나에 신청·구매·입금·수령 확인을 묶은 방향은 적절하다. 반팔티 다음 사업에도 재사용할 수 있는 범위다. 추가 기능보다 주문 데이터의 일관성, 실패 후 복구, 운영자가 자주 쓰는 작업의 정리가 먼저다.

- 굿즈와 일반 신청을 구분하되 같은 주문 모델을 사용하는 구조를 유지한다.
- 금액은 서버가 계산하고 주문 항목에 당시 단가를 남기는 방향을 유지한다.
- 학번 원문 대신 해시를 사용하고 공개 응답을 별도로 만드는 구조를 유지한다.
- 입금 전 본인 취소, 관리자의 일괄 처리, 기존 배부 시트 미리보기는 실제 운영 흐름에 맞는다.
- 반팔티 확인 기능의 캠페인 통합은 적절하나, 기존 데이터 이전과 기존 링크 도착 화면이 함께 검증되어야 한다.
- PG, 회원가입, 만능 폼 빌더, 다상품 장바구니, 과비 API 가격 연동, 홈 전체 개편은 이번 범위에서 제외한다.

## 관리자 정보 구조 제안

현재 13개 카드가 같은 크기와 강도로 나열된다. 자주 하는 운영 업무와 가끔 수정하는 기준 데이터가 섞여 있고, “행사 관리”와 “학생회 이벤트”는 이름만으로 차이를 알기 어렵다. 기능을 삭제하지 않고 작업 목적에 따라 묶는다. URL은 유지하고 표시 이름과 탐색 구조를 바꾼다.

| 그룹 | 표시 이름 → 기존 경로 |
|---|---|
| 신청·사업 운영 | 이벤트 신청·구매 → `/admin/campaigns`, 간식 위시리스트 → `/admin/snack-wishes` |
| 소식·소통 | 공지사항 → `/admin/notices`, 행사 사진·갤러리 → `/admin/events`, 커뮤니티·건의 → `/admin/community`, 홈 팝업 → `/admin/popup` |
| 학과·학습 정보 | 학습자료 → `/admin/resources`, 수업 정보 → `/admin/courses`, 전공서적 → `/admin/books`, 교수진 → `/admin/professors`, 건물·평면도 → `/admin/buildings` |
| 학생회·사이트 설정 | 학생회 구성원 → `/admin/members`, 사이트 설정 → `/admin/site` |

### 공통 관리자 레이아웃

- 인증을 유지하는 protected layout에 공통 헤더·탐색을 둔다. 각 페이지의 중복 헤더는 순차적으로 제거한다.
- 데스크톱은 4개 그룹의 사이드 내비게이션, 모바일은 현재 위치와 메뉴 버튼을 제공한다. 모바일 메뉴는 긴 경우 독립 스크롤되고 키보드 초점이 정상 복귀해야 한다.
- 모든 화면에 현재 메뉴 활성 표시와 `관리자 > 그룹 > 화면` 경로를 제공한다. 상세 페이지는 목록으로 돌아갈 수 있어야 한다.
- 대시보드는 4개 그룹을 명확히 분리한다. 자주 쓰는 바로가기는 이벤트·공지·커뮤니티 정도로 제한하고 실제 운영 빈도에 따라 조정한다.
- 새 통계 API나 개인화는 추가하지 않는다. 기존에 계산 가능한 숫자만 보여 주며 실패를 0건으로 표시하지 않는다.
- 메뉴 정의는 한곳에서 관리해 대시보드와 내비게이션의 이름·URL이 어긋나지 않게 한다. 보호 경계는 클라이언트 메뉴가 아닌 기존 서버 인증에 둔다.
- 색은 상태·주요 행동에 집중한다. 메뉴마다 다른 강조색, 큰 이동 효과, 모든 카드의 동일한 시각적 강조를 줄인다.

### 캠페인 상세 화면

상단에는 제목, 공개/접수/수령 확인 상태, 공개 페이지 보기, 목록 이동만 둔다. 상태는 “공개 여부”, “신청 접수 여부”, “수령 확인 여부”를 구분해 안내한다.

| 탭 | 기본 구성 |
|---|---|
| 신청 목록(기본) | 상태 요약 → 검색·필터 → 목록. 행별 주 행동 1개와 보조 메뉴. 선택했을 때만 일괄 작업 표시 |
| 수령 확인 | 확인 기능이 켜졌을 때만 노출. 미응답/받음/못 받음, 항목별 희망 처리와 수량 집계 |
| 설정 | 기본 정보·상품/옵션·신청 조건·입금 안내·수령 확인으로 섹션 분리. 영어 입력 등 부가 필드는 접기 |
| 데이터 관리 | 가져오기 미리보기·실행과 전체 CSV. 교체 작업은 삭제 범위·건수를 실행 전에 명시 |

- 설정과 수령 확인을 별도 새 URL로 늘릴 필요는 없다. 탭 상태를 query로 보존해 새로고침·뒤로가기가 자연스럽게 동작하게 한다.
- 목록의 “현재 필터 이메일 복사”와 “선택 이메일 복사”는 범위와 건수를 표시한다. 전체 CSV라면 “전체 CSV”라고 쓴다.
- 입금 취소와 대기로가 같은 동작이면 하나로 합친다. 취소·복구처럼 실수 비용이 큰 행동은 보조 메뉴로 옮긴다.
- 저장 실패 시 입력을 보존하고 재시도를 제공한다. 저장 중 중복 제출을 막으며 미저장 상태는 현재 탭을 넘어 명확히 표시한다.
- 긴 신청 목록은 모바일에서 카드/요약 행으로 핵심 정보와 주 행동을 먼저 노출한다. 상세 메모·연락처는 필요할 때 펼친다.

## 권장 기본값과 별도 정책 결정

### 개발자가 바로 적용할 기본값

- 새 캠페인은 비공개로 만들고, 접수 기간·계좌·가격을 확인한 뒤 공개한다.
- 수령 확인용 캠페인의 접수 종료와 확인 종료는 독립적으로 취급한다.
- CSV 적재는 미리보기 선행, 교체는 기본 해제, 실패 시 기존 주문 보존을 원칙으로 한다.
- 기존 링크와 주문 스냅샷을 보존하고, 오류를 빈 목록·0건·완료로 바꾸지 않는다.
- 기존 디자인 시스템과 컴포넌트를 재사용한다. 작은 수정은 새 라이브러리 없이 처리한다.

### 운영자가 결정해야 할 정책

- 중복 신청을 허용할지, `maxPerPerson`을 주문 1건 또는 동일인의 누적 신청에 적용할지.
- 반팔티의 최종 단가·구분별 가산, 공개/접수/수령 확인 마감 시각, 연락 방법.
- 마감일 없는 캠페인의 개인정보 보유 기준과 운영 종료 절차. 구현과 개인정보처리방침을 함께 맞춘다.
- 환불·교환의 실제 승인·완료 절차. 현재 “희망” 응답을 처리 완료로 해석하지 않는다.

정책 미확정 사항을 임의로 확정해 운영 데이터에 적용하지 않는다. 개발은 검증·오류 복구·메뉴 정리 등 독립 작업부터 진행할 수 있다.

## 작은 PR 단위의 진행 계획

1. **데이터 보호와 API 정합성**: 검토 결과의 배포 차단 항목을 먼저 수정하고 동시성·실패 경로 회귀 테스트를 추가한다.
2. **공개 신청·확인 흐름**: 오류 복구, 상태 표시, 제출 전후 흐름을 고친다. 모바일과 한·영 화면을 검증한다.
3. **관리자 공통 탐색**: 13개 메뉴를 4개 그룹으로 묶고 공통 레이아웃을 적용한다. 기능 URL과 인증은 유지한다.
4. **캠페인 상세 정리**: 신청 목록을 기본 탭으로 바꾸고 수령 확인·설정·데이터 관리로 작업을 나눈다. 상태 변경·선택·필터 범위를 명확히 한다.
5. **이전·배포 리허설**: 격리 DB에서 기존 데이터 이전, 적재, 신청, 확인, 관리자 처리, 내보내기를 한 바퀴 수행한다. 결과와 롤백 절차를 기록한다.

각 PR은 범위·재현 단계·변경 후 동작·검증 결과를 적는다. 전체 화면 재작성과 API 정책 변경을 한 PR에 섞지 않는다.

## 검증 및 배포 전 조건

- 코드 수정 전에 해당 Next.js API의 로컬 가이드 `node_modules/next/dist/docs/`와 저장소 지침을 읽는다.
- 타입 검사·관련 린트·프로덕션 빌드와 기존 캠페인 테스트를 실행한다. 실패를 기존 문제로 판단했다면 근거와 영향 범위를 남긴다.
- 테스트는 운영 DB에서 실행하지 않는다. 인증 우회나 공개 쓰기 권한 완화로 테스트를 통과시키지 않는다.
- 브라우저에서 360px 안팎 모바일·데스크톱, 키보드 이동, 한·영 전환, 빈 상태·404·API 실패·재시도를 확인한다.
- 신청 → 주문번호·입금 안내 → 본인 조회 → 입금 전 취소 / 입금 후 취소 거부 → 관리자 입금·수령 → 수령 응답 → CSV를 검증한다.
- 캠페인 비공개, 접수 전·마감 후, 수령 확인 마감 전후를 각각 검증한다. 한국 시간 입력과 저장·재표시의 일치를 확인한다.
- 배포 전 DB 백업·이전 결과 대조·실패 시 복구 절차를 준비한다. 기존 `/shop/check` 도착 캠페인과 이전 주문 조회를 검증한 뒤 운영 안내에 사용한다.
- 이 문서의 검토만으로 배포 가능 판정을 내리지 않는다. 최종 커밋·검사 결과·이전 리허설 증거를 기준으로 판단한다.

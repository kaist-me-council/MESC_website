## 2. 공지 첨부 및 저장

### U1. Drive 이동 인자 오류

- 근거: `app/api/admin/upload-file/to-drive/route.ts:42`, `lib/drive-oauth.ts:289`.
- 호출은 `(token, "공지 첨부", parentFolderId)`지만 선언은 `(token, parentId, name)`이다.
- 실패 조건: Drive가 연결된 상태에서 첨부 이동. `공지 첨부`가 부모 ID로 전달되어 실패하고 Blob으로 우회한다.
- 로컬 mock에서 인자 역전과 `moved:false`를 확인했다. 실제 Drive 업로드 검증과는 다르다.

수정: 인자를 올바르게 전달하고, 같은 string 타입끼리 혼동하지 않도록 `{ accessToken, parentId, name }` 객체 인자로 바꾸는 것을 권장한다.
이 helper의 모든 호출부를 확인하되 관계없는 Drive 작업의 동작은 바꾸지 않는다. 기존 Blob 폴백은 유지한다.
회귀검증: helper 호출 인자 단위검사, 폴더 존재/미존재 분기, Drive 미연결·실패 시 Blob 첨부 유지.
실서비스 수용검증은 별도 승인된 검증 저장소에서 실제 부모 폴더·저장 위치·다운로드를 확인한다.

### U2. 공지 저장 실패 시 입력 보존

- 근거: `app/admin/(protected)/notices/page.tsx:80–100`.
- `fetch`의 HTTP 상태를 확인하지 않고 `resetForm()`을 실행하며, 예외 시 `submitting` 해제도 보장하지 않는다.
- 제목 201자를 넣으면 UI는 제출하지만 API가 400을 반환하고 폼과 첨부가 사라진다. mock으로 확인했다.
- 이 저장 로직은 이전부터 있었지만 최신 첨부 흐름에서도 계속 영향을 준다.

수정: 동기적인 중복 제출 가드와 `try/catch/finally`를 두고, 성공 응답을 검증한 뒤에만 폼을 초기화한다.
400·401·500·네트워크 단절·비정상 JSON은 사용자 오류로 표시하며 제목·본문·첨부를 보존한다.
입력 길이 제한은 서버 계약과 맞추되 클라이언트 제한만으로 서버 검증을 대체하지 않는다.
저장이 성공한 뒤 목록 갱신만 실패하면 "저장 완료, 목록 갱신 실패"로 구분하고 목록만 재조회한다.
목록 조회 실패를 저장 실패로 표시하여 같은 공지를 다시 등록하게 만들지 않는다.
서버가 저장했으나 응답이 유실된 경우는 성공 여부 미확정으로 안내하고 무조건 자동 재등록하지 않는다.
회귀검증: 각 실패의 입력 보존·잠금 해제, 성공 시 1회 저장, 성공 후 목록 실패 시 재저장 없는 복구.

### U3. 기존 첨부 ID와 다운로드 URL 보존

- 근거: `app/api/notices/[id]/route.ts:55–66`, `lib/upload-rules.ts`의 `attachmentDownloadUrl`.
- PUT은 모든 첨부를 삭제하고 다시 만든다. Drive 다운로드 URL은 첨부 DB ID를 사용한다.
- 실패 조건: 학생이 공지를 열어둔 뒤 관리자가 제목만 수정. 학생이 기존 첨부 링크를 누르면 404가 된다.

수정: 기존 첨부 ID를 보존하고 추가·제거된 행만 반영한다. 유지되는 파일의 새 ID를 만들지 않는다.
PUT에서 `attachments` 키가 없으면 변경 없음, 명시적 `[]`는 모두 제거라는 계약을 정하고 테스트한다.
기존 ID는 반드시 현재 공지 소유인지 검사한다. 다른 공지의 첨부 ID는 거절한다.
기존 ID의 저장소 식별자·URL을 클라이언트가 덮어쓰지 못하게 하고, 기존 데이터는 서버에서 읽는다.
본문 수정과 첨부 DB 변경은 트랜잭션으로 묶는다. 삭제할 파일은 변경 전 목록에서 차집합으로 계산한다.
실파일 정리는 DB 커밋 성공 후에만 수행한다. DB 실패 시 기존 다운로드 파일을 먼저 지우지 않는다.
공유 참조 여부를 확인하고, 정리 실패가 저장 성공을 실패로 바꾸지 않게 로그/재정리 경로를 둔다.
새 업로드 목록에서 제거하거나 편집 취소한 임시 파일의 처리 정책도 U4의 작업 세션과 함께 정한다.
회귀검증: 제목만 변경·첨부 유지·추가·삭제·키 생략·명시적 빈 배열·다른 공지 ID 거절·DB 실패·정리 실패.
첨부 유지 후에는 이전 URL과 현재 URL 모두 같은 파일을 내려줘야 한다.

### U4. 업로드 작업을 시작한 폼 세션에 귀속

- 근거: `app/admin/(protected)/notices/page.tsx:170–189`, `:251`, `:388–389`.
- 완료 파일은 현재 `attachments`에 추가하지만 다른 공지 수정/취소 버튼은 업로드 중에도 활성이다.
- 실패 조건: A에서 업로드 시작 → B 수정 또는 작성 취소 → 업로드 완료. A의 파일이 B/새 폼에 들어간다.

수정: 폼 전환·초기화 시 증가하는 세션 ID를 만들고 업로드 시작 시 캡처한다.
완료·실패·진행문구·저장소 표시 등 모든 비동기 상태 반영 전에 같은 세션인지 확인한다.
업로드 중 다른 공지 수정·현재 편집 취소·중복 파일 선택을 일관되게 막거나 명시적으로 작업을 취소한다.
UI disabled와 별도로 ref 기반 실행 가드를 두어 같은 이벤트 루프의 중복 시작도 막는다.
네트워크 취소를 지원하는 단계는 AbortController 등 실제 취소를 연결하고 타이머를 해제한다.
`Promise.race`의 5분 상한은 원래 작업을 취소하지 않는다. 시간 초과 후 늦게 끝난 작업도 세션 가드로 무시한다.
완료되지 않은 작업이 새 폼의 `uploading=false`나 진행문구를 덮어쓰지 않게 한다.
회귀검증: 지연 upload/verify/move 각각에서 전환·취소·시간 초과·재시작을 교차하고 첨부 혼입이 없는지 확인.

## 3. 푸시 알림

### P1. 브라우저 구독과 서버 등록 상태를 구분

- 근거: `components/notification-toggle.tsx:59–62`, `:97–106`.
- 브라우저 subscription 생성 후 서버 POST가 실패하면 catch의 `detect()`가 subscription만 보고 `on`을 표시한다.
- 새로고침 후에도 서버에 endpoint가 없는 채 켜짐처럼 보일 수 있다. 여러 토글의 로컬 상태도 공유되지 않는다.

수정: browser subscription 존재와 서버 등록 확인을 별도 상태로 모델링한다.
앱의 공유 provider/context에서 초기 동기화를 1회 수행하고, 기존 endpoint 등록은 멱등 upsert로 재시도한다.
서버 등록 실패는 "등록 실패/재시도" 상태로 남긴다. 서버 확인 전 `on`으로 돌아가지 않는다.
토글 마운트마다 subscribe를 실행하여 사용자가 의도적으로 끈 알림을 되살리지 않는다.
명시적 off 상태와 진행 중 동기화의 경합을 막고, 모든 토글이 상태·busy·오류를 공유하게 한다.
Notification 권한 요청은 사용자 클릭에서만 수행한다. 자동 권한 요청·신규 로그인 도입은 하지 않는다.
회귀검증: 서버 등록 400/500/offline, 재마운트, 기존 구독 재등록, 두 토글 동기화, off 직후 늦은 응답.

### P2. 발송 실패와 구독자 0명을 구분

- 근거: `lib/push.ts:46–64`, `app/api/notices/[id]/notify/route.ts:24–37`.
- VAPID 설정 또는 구독 DB 조회 실패에도 `{sent:0, failed:0, pruned:0}`를 반환하여 정상 0건과 구분하지 못한다.
- 환경변수가 실제로 누락되었다는 주장이 아니라, 그런 실패를 숨기는 코드 경로가 확인됐다는 의미다.

수정: 결과에 `status`/안전한 오류 코드를 두고 미설정·조회 실패·구독자 없음·부분 실패·완료를 구분한다.
관리자 발송 API와 화면은 그 결과를 표시한다. 토큰·endpoint·내부 오류 원문은 노출하지 않는다.
발송 요청별 timeout 및 전체 작업의 유한한 상한을 두고 UI의 busy 해제를 보장한다.
`app/api/notices/route.ts`의 공지 저장 성공은 유지한다. 알림 실패를 공지 저장 실패로 돌리지 않는다.
저장과 발송 결과를 별도 필드/작업으로 표현하고, 실패 시 기존 공지를 다시 생성하지 않고 알림만 재시도한다.
서버리스 응답 후 처리 보장이 없는 무조건적인 fire-and-forget으로 바꾸지 않는다.
회귀검증: 미설정·조회 실패·0구독·일부 실패·요청 지연에서 결과 구분 및 저장된 공지 1건 유지.

### P3. 알림 클릭으로 다른 편집 탭을 이동시키지 않기

- 근거: `public/sw.js`의 `notificationclick` 두 번째 client 순회.
- 대상 URL 탭이 없으면 첫 기존 window에 `navigate(target)`를 호출한다.
- 실패 조건: 관리자 공지/캠페인 작성 중 알림 클릭. 편집 탭이 바뀌어 미저장 입력을 잃을 수 있다.

수정: 정확한 대상 URL의 탭이 있으면 focus만 한다. 없으면 새 창/탭을 연다.
관련 없는 탭에는 navigate를 호출하지 않는다. 대상 URL은 같은 origin인지 URL 파싱 후 확인한다.
회귀검증: 대상 탭 있음·없음, 여러 기존 탭, 미저장 폼, 부정한 URL에서 기존 탭 URL·입력 불변.

### P4. 두 알림 토글의 상태 공유

- 근거: `app/notices/page.tsx:96`, `components/Footer.tsx:74`, `components/notification-toggle.tsx:48`, `:68–70`, `:103`, `:126`.
- 공지 페이지와 푸터가 별개의 컴포넌트 상태를 가진다. 한쪽에서 켜거나 꺼도 다른 쪽은 최초 조회 상태로 남는다.
- 실패 조건: 공지 페이지 토글로 구독 변경 후 같은 화면의 푸터 토글을 확인하면 상태가 서로 다르다.

수정: P1의 공유 provider/context를 두 위치의 공통 소유자로 사용한다. 상태 변경마다 두 인스턴스를 함께 갱신한다.
각 토글의 독립 detect/subscribe 실행을 없애고, 중복 마운트가 권한 요청이나 구독 생성으로 이어지지 않게 한다.
회귀검증: 페이지→푸터 및 푸터→페이지 양방향 on/off, 등록 오류, busy 중 다른 토글 클릭에서 상태 일치.

## 4. 방문자 식별과 좋아요

### V1. 첫 방문자 토큰 확정 후 요청 보내기

- 근거: `lib/visitor.ts:25–29`, `components/view-tracker.tsx:10–15`, `app/api/views/route.ts:45` 및 좋아요 API.
- 쿠키 없는 조회·좋아요 요청이 병렬이면 각각 랜덤 토큰을 발급하고 Set-Cookie가 서로 덮어쓴다.
- 좋아요가 이전 토큰에 기록되어 새로고침 후 사라져 보이거나 같은 브라우저에 중복 기록이 생길 수 있다.

수정: 방문자 초기화 완료 후 조회·좋아요가 같은 확정 쿠키로 실행되도록 공통 초기화 경로를 만든다.
같은 탭은 공유 init promise로, 두 탭의 최초 동시 진입은 별도 교차탭 동기화로 다룬다.
예: Web Locks 지원 시 초기화 잠금을 공유하고 잠금 획득 후 서버에서 기존 쿠키 존재를 재확인한다.
미지원 브라우저 fallback과 남는 한계를 명시한다. 같은 탭 promise만으로 두 탭 문제까지 해결했다고 보고하지 않는다.
토큰은 httpOnly 쿠키로 유지한다. JS에 평문을 노출하거나 localStorage로 옮기지 않는다.
SSR 렌더 중 쿠키 쓰기나 전체 사이트 no-store로 우회하지 않는다. 초기화 실패 시 기록을 보류하고 재시도를 안내한다.
회귀검증: 새 브라우저의 조회+좋아요 동시 요청, 응답 역순, 두 탭 최초 진입, 재방문에서 식별자·집계 일관성.

### V1 구현 보강: 좋아요 재시도도 같은 상태로 수렴

- 근거: `app/community/posts/[id]/like-button.tsx:13–29`, `app/api/posts/[id]/like/route.ts`의 토글 트랜잭션.
- 서버가 좋아요를 저장했지만 응답만 유실되면 UI는 이전 상태로 복구한다. 재시도 POST는 좋아요를 취소한다.

별도 10번째 발견이 아니라 V1의 좋아요 복구 구현 권장사항이다. `PUT { liked: true | false }`처럼 목표 상태를 명시하고 같은 요청 재시도가 같은 결과가 되게 한다.
서버는 고유키와 트랜잭션으로 실제 상태가 변한 경우에만 집계를 증감한다. 현재 상태와 count를 함께 반환한다.
클라이언트는 실패한 목표 상태를 기억해 그대로 재시도하거나 최신 상태를 재조회한다.
기존 POST 클라이언트의 호환/전환 정책도 같은 변경에서 정한다. V1 초기화 이후 요청해야 한다.
회귀검증: 저장 후 응답 유실→재시도, true 반복, false 반복, 병렬 동일 상태, 반대 상태 요청에서 집계 정확성.
